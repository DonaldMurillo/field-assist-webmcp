# Title

Field Assist — live spatial guidance for remote support

## One-line Summary

Field Assist lets Codex and a human support representative turn a live phone camera into verified, object-tracked guidance through WebMCP.

## Problem

Remote support often fails at the last few inches. The operator holds a phone with one hand while trying to interpret instructions such as “press the button underneath” or “use the port on the left.” The expert can see the video but cannot point into the operator's physical space, and ordinary chat has no durable understanding of which object, control, or instruction is current.

This creates a particularly poor experience for equipment repair, device setup, accessibility support, field service, inspection, and other hands-busy work. A plausible instruction is not enough: the target must be identified, confirmed, tracked, delivered to the phone, and cleared when it is no longer valid.

## Solution

Field Assist creates a two-device support session. The operator scans a one-time QR code, shares a rear-camera stream over peer-to-peer WebRTC, and describes the problem by selecting a starter or entering a free-form request. The support representative sees the same scene in a desktop console.

Codex joins through the support page's WebMCP tools. It loads the app-provided operating contract, inspects the live request and scene, uses vision and product knowledge to form an object hypothesis, asks the operator for confirmation when needed, and registers only visually grounded devices and controls. It can then send a large phone-visible instruction and draw an arrow on a verified control. OpenCV, Depth Anything, and device orientation help the browser keep that arrow associated with the physical target as the camera moves.

The application never embeds a separate model endpoint. Codex is the runtime agent, and WebMCP is its authenticated command boundary.

## Why This Matters

Field Assist is a strong WebMCP use case because the browser contains live, private, rapidly changing state that cannot be represented by a generic prompt or brittle UI automation. WebMCP exposes the application's meaning: scenes, stable object IDs, control-level targets, operator questions, delivery receipts, tracking confidence, room context, and reversible annotations.

The user experience becomes faster and safer because:

- The operator does not install an app or create an account.
- Camera media remains peer to peer instead of passing through the application server.
- Instructions appear where the operator is already looking: on the phone camera.
- The agent can ask bounded questions and receive backend-synchronized answers.
- Broad device identification is kept separate from precise control localization.
- Guidance disappears or requests reacquisition when tracking confidence is no longer sufficient.
- The human support representative can inspect, correct, compose, or remove the same shared guidance.

People and agents can now collaborate around a physical object: the person supplies intent and confirmation, Codex supplies visual reasoning and product knowledge, and the application supplies a safe realtime interaction model.

## Why WebMCP

**Why this use case is a strong fit for WebMCP.** Field Assist depends on live, authenticated browser state: a private camera session, changing scene geometry, operator answers, tracking confidence, and guidance-delivery receipts. WebMCP lets Codex work with those concepts directly through semantic, page-scoped tools instead of guessing at UI controls or receiving a giant screenshot-and-prompt dump.

**How it creates a better user experience.** The operator keeps one hand on the phone and receives large, timely instructions plus an arrow associated with the physical control. Codex and human support share the same backend-authoritative scene, conversation, and banner state, so the operator does not need to repeat context or translate vague chat directions into physical action.

**What people and agents can do together that was difficult before.** A person can supply intent, judgment, and physical confirmation while Codex contributes vision, product knowledge, structured questioning, and rapid guidance. Together they can identify an unfamiliar device, confirm the right object, locate a small control, guide the operator toward it, and withdraw the annotation when tracking becomes unsafe—all inside the live support session.

**How WebMCP was implemented.** The authenticated support page exposes twenty-five tools generated by GoFastr through `document.modelContext.registerTool(...)`. Read tools return versioned session and scene state; mutating tools call the same authenticated Go handlers as human controls and must include the current `contextVersion`. Landing and operator pages expose no support tools. WebRTC carries peer-to-peer video, while GoFastr WebSockets synchronize signaling and compact semantic state.

## How We Used AI

Codex is both the agent operating the finished application and the primary development environment.

At runtime, Codex can:

- Read the user's request and the versioned Field Assist operating protocol through `get_app_info`.
- Inspect structured scene, conversation, room, tracking, question, and delivery state.
- Use vision to locate visible devices and controls in the peer video shown by the browser.
- Use existing product knowledge or official manufacturer information to narrow a control hypothesis.
- Register a containing device and its actionable control as separate semantic objects.
- Ask the operator a two-to-four-choice question when visual identity is ambiguous.
- Send concise instructions to the large amber phone banner.
- Draw and remove reversible guidance on a verified `device-control` target.
- Reinspect and recalibrate when the scene changes or confidence drops.

Identity, localization, tracking, and delivery remain separate confidence signals. The server rejects precision arrows on broad devices, rejects mutations without the current app-context version, and records whether the phone actually rendered an instruction. AI suggests and guides; it does not silently claim that a physical action happened.

## Key Features

- Ten-minute, single-use operator QR links with immediate token removal after exchange.
- Video-only peer-to-peer WebRTC between the operator phone and support desktop.
- Twenty-five authenticated, support-page-only WebMCP tools rendered from one Go declaration source.
- Free-form and starter requests without hardcoded agent behavior.
- Shared two-way operator, support, and Codex conversation.
- Backend-authoritative phone banner with compose, replace, remove, and rendered-delivery state.
- Server-versioned scene graph with separate device and `device-control` objects.
- Bounded operator questions with visible answer acknowledgment on both screens.
- Support-side OpenCV homography/PnP tracking and Depth Anything V2 relative-depth inference.
- Lightweight phone tracking and short-lived DeviceOrientation correction over a peer data channel.
- Object-relative arrows that are suppressed when geometry becomes unsafe.
- Responsive, one-handed operator UI and a desktop support console with progressive diagnostics.
- Agent-readable `/llms.txt`, `/llm.md`, `/llm-pages.md`, `/tools/llm.md`, and `/stack/llm.md` documentation.

## Architecture

Field Assist is one Go service built on the published GoFastr `v0.75.0` module, with no local framework replacement. GoFastr provides the server-rendered application host, typed handlers, middleware, WebSocket hub, UI components, lifecycle endpoints, logging, static plugin assets, and experimental WebMCP bridge.

The authenticated support document registers tool definitions through GoFastr. The generated browser bridge calls `document.modelContext.registerTool(...)`, while landing and operator documents expose no support capabilities. Every state-changing page tool uses the same authenticated HTTP handlers as the corresponding human control and must include the session-bound `contextVersion` returned by `get_app_info`.

Browser code owns the APIs that must run next to the media: `getUserMedia`, `RTCPeerConnection`, Canvas overlays, OpenCV 5, ONNX Runtime Web, Depth Anything V2 Small, and DeviceOrientation. Camera pixels, descriptors, depth maps, SDP, ICE candidates, and orientation samples are not stored by the application server. GoFastr carries signaling and compact semantic state; the phone receives only the active normalized target geometry required to render guidance.

The public deployment runs as a single VPS-hosted instance because demo sessions are ephemeral and stored in memory. Public STUN is enabled, and TURN can be supplied through `ICE_SERVERS_JSON` for restrictive network pairs.

## Testing Instructions

No account or credentials are required.

1. Open <https://webmcp.donaldmurillo.com> in Codex's built-in browser using a WebMCP-capable model, or in Google Chrome with WebMCP enabled.
2. Select **Start a field session**.
3. Scan the QR code with a phone, open the one-time operator link, and select either the controller scenario or free-form help.
4. Allow rear-camera access on the phone.
5. In Codex, inspect the page's Site tools and call `get_app_info`, followed by `inspect_scene`.
6. Use the live video and the user's request to identify a device. Ask the operator to confirm it when necessary.
7. Register the containing device, then register a verified physical control as `device-control`.
8. Send a phone banner and call `draw_arrow` on the control.
9. Move the phone closer, farther, and sideways. The arrow should remain associated with the control or disappear and request reacquisition when confidence becomes unsafe.
10. Use **Display status** to inspect connection, tracking, perception, and banner-delivery state. Use **Remove** to clear the instruction.

## Known Limitations

- Monocular depth is relative, not metric, and does not create a persistent SLAM map or LiDAR-quality world model.
- Reflective, texture-poor surfaces can weaken feature tracking, especially when the target is partially outside the frame or viewed extremely close.
- Codex supplies the initial semantic localization from the visible browser frame; OpenCV and Depth Anything stabilize that grounded target rather than discovering arbitrary objects autonomously.
- STUN-only WebRTC can fail on restrictive NAT combinations. The application supports environment-provided TURN credentials but does not bundle a relay service.
- Sessions are in memory, require one application replica, and are invalidated by deployment restarts.
- The current Codex Site-tools path requires a compatible Codex model in the built-in browser; non-WebMCP browsers retain manual support controls.
